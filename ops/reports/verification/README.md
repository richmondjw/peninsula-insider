# The claim verification queue

PI-006. What lives in this directory, and what a person does with it.

## The files

| File | Written by | What it is |
|---|---|---|
| `verification-loop.json` / `verification-loop-<date>.md` | the nightly loop | the run report: what was looked at, what was refused, the shape of the backlog |
| `proposals.json` / `proposals-<date>.md` | the nightly loop | the review queue: field-level changes, each with the page it was read from |
| `decisions.jsonl` | `npm run verify:review` | the decision ledger, append-only. Not generated, never regenerated |
| `patches/*.patch` | `npm run verify:apply` | the prepared edit, for a person to read and apply |

Everything except `decisions.jsonl` is regenerated by a run. The ledger is
not: it holds acts a person took, and nothing can recompute those.

## Working the queue

```
npm run verify:proposals                                    run the loop, write the queue
npm run verify:review -- --list                             read it
npm run verify:review -- --show <id>                        one proposal in full
npm run verify:review -- --accept <id> --by "Name" --read "<url>"
npm run verify:review -- --reject <id> --by "Name" --note "<why>"
npm run verify:apply                                        prepare patches for what was accepted
git apply ops/reports/verification/patches/<id>.patch       you do this part
npm run verify:review -- --agreement                        how often the loop and a person agreed
```

`--read` is the page you opened yourself. It can be the source the loop read
or a different one you went and found. It cannot be absent: /how-we-check/
tells readers that every edit is made by a person who has looked at the thing
themselves, and this is where that is recorded.

## What none of this does

No command in this loop edits a content record. There is no flag that makes
one, and `scripts/verification-proposals.test.mjs` asserts that by reading the
sources rather than by trusting this file: `report.mjs` is the only module that
calls a filesystem write, it refuses any path outside a reports tree, and
`apply.mjs` imports nothing at all from `node:fs`.

The terminal artefact is a patch. A person runs `git apply`. Decision D5, when
it is taken, is a decision about that one command and nothing before it.

## What the loop will not carry

- A change the critic rejected on a second reading of the same page. A person
  who disagrees edits the record by hand, with their own name in the history.
- A check date, a licence, a permission, a credit, a byline or a verdict. Those
  are refused by the composer and refused again at review.
- A proposal missing its URL, its fetch date or its page digest. It cannot be
  walked back to anything, so there is nothing to decide about.

## One thing to know before you read a rank

Every proposal states where its source sits in precedence for that class of
claim, and what it is believed before. That ordering comes from
`next/src/data/source-precedence.json` and is reported exactly as written.

For closures, conditions and fishing rules the table currently believes a
commercial partner of ours very early, ahead of a news report and ahead of our
own notes from a visit. Whether it should is on the register as decision A29.
The loop does not correct it. It states it on every proposal so that nobody
relies on it without seeing it.
