## Whether this run can be trusted

These checks are the point of the proposal-only stage. They are the properties a write stage would have to keep, measured against the real corpus, so the write-scope decision has evidence rather than assurances.

| Check | Result | What it means |
|---|---|---|
| no-content-write | pass | the report-only loop must not alter a single byte of any content or data record |
| no-check-date-refreshed | pass | a successful fetch proves a page responded, never that a person read it and agreed, so no composed change may move a verification date |
| no-evidence-row-recorded | pass | a confirmation produces a PROPOSED evidence row for a person to accept; recording one automatically is the same check-date failure wearing a different field name |
| every-change-cites-evidence | pass | every proposed change must cite the fetched artifact it came from, by digest |
| every-escalation-states-a-question | pass | an escalation without a specific question and a default is a notification, and notifications are what a review queue dies of |
| outbound-limited-to-cited-sources | pass | the only outbound traffic permitted is a GET of a URL a record already cites |
| no-verdict-without-a-readable-source | pass | unreachable and blocked are source-health facts, never verdicts about a claim |
| every-proposal-is-auditable | pass | a proposal that cannot be walked back to a fetched page, by URL, fetch date and page digest, is a machine opinion wearing the clothes of a citation, and it may not reach a reviewer |
| no-proposal-applies-itself | pass | every proposal states on its own face that nothing applied it, so a proposal read in isolation still says what could and could not act on it |

## What the loop refused to do

A refusal is the loop declining to compose a change it cannot support. This count matters more than the findings: a loop that never refuses anything is a loop with no guard, and the guard is the component a write stage has to trust.

None this run, and on a production run that is the expected reading rather than a clean bill of health. The researcher in this stage is a deterministic detector set, and it proposes only what a page can establish, so it rarely offers the guard anything to refuse. The guard is exercised instead by the seeded fixtures in `scripts/verification-loop/fixtures/seeded-failures`, where a simulated model-backed researcher proposes a bumped check date, a licence read off a credit line and a first-person visit, and `scripts/verification-loop.test.mjs` asserts that all three are refused. That is where a write stage should look for evidence, because that is the traffic a write stage would actually carry.

## The review queue

0 of those changes were written up as proposals, of which 0 are decidable. A proposal carries the seven things a reviewer needs and a patch table does not: the claim, what the record says now, what is proposed, the URL read, when it was read, what kind of publisher that is, and where that kind sits in precedence for this class of claim. The rest are shown with the reason they cannot be decided here, which is usually that the critic threw the change out. The loop will not carry a change its own second reading rejected, and a person who disagrees edits the record by hand with their own name on it.

## What a write stage would still need

- A run of this loop against human decisions on the same batch, so the critic has a measured false-positive and false-negative rate rather than an assumed one.
- A decision on write scope (D5). Nothing here presumes one, and the guard list in `compose.mjs` is the narrowest defensible starting point, not a proposal.
- Evidence coverage for the three blind-spot classes. A write stage that cannot see opening hours, accessibility or rate changes would be writing with a third of the reader-facing surface out of view.
- An owner for the dead and blocked citations. Roughly a third of this corpus cannot be checked from its own recorded source, and no amount of loop improves that number.
