**Two entries name no photographer.** `home-cover.webp` and `places-hub-hero-01.webp` both record the Photographer as "Wikimedia Commons contributor", which is a sentence about where the image came from rather than an attribution. Every licence in this file except one is a CC-BY variant, and attribution is the condition of the grant, so a record carrying that string satisfies nothing.

**The file disagrees with itself 0 times.**

No two entries in the file state different things about one original URL.

## Set against the records

Every image record is placed in one of five states. The middle three are the ones the ticket asked for; the other two are reported because leaving them out would make the coverage look better than it is.

| State | Records | What it means |
|---|---|---|
| file-only | 100 | the file has an answer and the record has nothing. The backfill queue |
| conflict | 15 | both state a grant and they are different grants. A person has to decide |
| placeholder | 29 | the record holds `unknown`, `tmp-*` or `other-licensed`, which assert no grant, and the file names one |
| agree | 3 | both say the same thing |
| neither | 264 | nobody has written anything down |
| record-only | 818 | the record knows something the file does not |

Not one record in the corpus carries a `creator`, a `sourceUrl`, a `permission`, a `rightsHolder` or a `rightsEstablishedOn`. So every disagreement below is a disagreement about the coarse `license` bucket, which is the only rights field the corpus has ever populated, and which until 2026-09-14 carried a schema default that manufactured a media-kit grant out of an absent value.

That is also why `agree` is zero and should not be read as a failure. A record can only agree with the file about a field it has, and there is no record with a photographer or a source URL to agree about. 100 records agree about the licence bucket and have nothing in the other three fields, which is why they sit under file-only: the state of a record is the worst thing found on it, not the best.

## The decision this is waiting on

Register item A15 is unresolved: whether a licence recorded in a repository file may be written onto a content record as that record's rights claim. Nothing in this branch does it. The apply path exists, it has been dry-run, and it has not been run.

**The question.** May `next/scripts/apply-image-rights.mjs --confirm` write the photographer, the source URL, the licence text and the matching enum bucket from LICENSES.md onto the records that use those images, where the source page has been fetched and corroborates both the licence and the photographer, stamping `rightsEstablishedOn` with the date of that check?

**The recommended default, if no answer comes: no, not as a blanket run.** The argument is in this report rather than in caution. Six of the twenty-two sources did not corroborate what the file says about them, one of them wrong in both the licence and the photographer, and the file was assembled by the same kind of process that produced the records it would be correcting. A document wrong about one entry in four is a document to read, not a document to copy.

**What to do instead.** Run the apply path scoped, with a person on each batch. It takes `--only`, so the first pass is the shared hero images that carry the most exposure for the fewest decisions:

```
node scripts/apply-image-rights.mjs \
  --checked-on <the date you read the pages> --checked-by "<you>" \
  --only place-red-hill-01.webp \
  --only place-main-ridge-01.webp \
  --only place-mornington-01.webp \
  --only place-merricks-01.webp \
  --only place-flinders-01.webp \
  --only place-sorrento-01.webp \
  # then read the patch, then add --confirm
```

That is 14 images to look at and 91 entity records that follow from them, against 147 records and 24 images in the blanket run. The dry run over the whole file is committed beside this report as `2026-09-14-image-rights-dry-run.patch`; it plans 129 records and refuses 47, and nobody has applied it.

**And one thing to fix whatever is decided.** The Nazaaray entry in LICENSES.md is wrong about both the licence and the photographer, and the two entries reading "Wikimedia Commons contributor" can be replaced with the names Commons gives. Those are corrections to the file, they need no decision about A15, and they should happen before anything copies out of it.
