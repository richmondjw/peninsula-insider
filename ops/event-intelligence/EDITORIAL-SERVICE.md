# Durable editorial service candidate

Disabled by default; the example is intentionally nonoperational. `runEditorialService({enabled:false,configPath,configHash,expectedRoot,now})` is a callable preparation step for future runner integration, not an installed scheduler. Config16KiB requires explicit enabledtrue plus independent SHA256 pin and expected canonical realpath root. Registry bytes are independently pinned; producer registry array hash is also bound. The service reads actual website inventory itself. Prior receipts and episode state are loaded only via latest.json, which atomically binds immutable service-receipt.json and episode-ledger.json byte hashes. Research/caller receipts and unbound root episodes.json cannot supply state. Each committed receipt records its previous head for later outbox replay; sender eligibility must follow this committed chain, not scan every orphan directory.

A service.lock is acquired exclusively and carries random nonce, host/PID and process-start identity (Linux boot ID/start ticks). Existing or unknown lock is retained, returns busy and writes one bounded lock-blocked observation where safe. Owned lock removal requires acquired file dev/inode, nonce and process identity match. No stale-lock deletion or restart is automatic.

Unique run pending/service receipts use exclusive creation and fsync. Producer-owned captures/receipts are flushed before service admission. Linux directories are fsynced; Windows cannot provide this directory durability through this implementation and receipts explicitly report directorySyncSupportedfalse. Preparation CAS failures retain failure.json and emit no success pointer. If persistence itself fails, the thrown error reports persistenceFailure; no delivered/admitted claim follows.

Cadence is at most12hours and refresh is requested15minutes before the earliest proposal expiry, with15-minute retry for held/failure alerts. Config, packet, registry or actual inventory changes invalidate stored not-due state. The caller must honour deadline and must not equate successful preparation with publication. No unresolved human hold is removed by this service.

Per-run immutable episode-ledger.json preserves open/resolved episodes, capped2000 with backpressure rather than deletion. Ledger and service receipt are fsynced before the atomic head commit; interrupted uncommitted receipts cannot suppress the next actionable alert. Root episode projections are not authoritative. New actionable alerts produce one durable outbox proposal per open episode; a fresh successful attempt resolves the episode and proposes recovery. Existing human acknowledgements remain unchanged; humanAcknowledgedfalse is not changed to true by dashboard delivery. This module sends no messages. Immutable service receipts hold outbox proposals for a later sender; there is no delivery/acknowledgement integration yet.

Prepare trusted build plan and pinned registry/captures. Refuse human/source/inventory drift. Apply in isolated review checkout via file CAS, preserving all unrelated records. Run accepted build/independent gates, then use the existing release workflow with user-authorised publication. On failure retain live version, record transaction failure; on evidence expiry/withdrawal prepare a separate CAS-bound withdrawal and immediately fail closed through the public reader clock. No direct repository push/deploy/source-state mutation exists in this service.

Storage configuration is mandatory: maxBytes256MiB–1GiB, maxRuns2–10000, reserveBytes at least192MiB (bounds worst-case escaping of fifteen2MB captures plus receipt overhead). Admission counts retained root files/directories with conservative max logical/allocated bytes (Windows allocation estimated at4KiB), requires configured reserve and64MiB actual filesystem margin, and pauses before collection if capacity is exhausted. History is never deleted. Capacity alerts are private observations, not delivered/acknowledged claims. This finite budget requires operational capacity management; it does not promise unlimited history.

Automatic approval review rejected a proposed pinned dead-lock quarantine because moving the lock would remove a safety control without exact authorisation. That helper was not added. Unknown locks remain untouched and actual crash tests stop at the preserved busy state.

Future clean-root Linux candidate: editorial-kernel-lock.py accepts explicit pinned configuration, expected root, pinned Node binary and worker source. It refuses every existing service.lock, requires a pinned kernel-root.json marker and linux-kernel-v1 mode, opens persistent kernel-advisory.lock with O_NOFOLLOW, acquires nonblocking flock, then execs the actual Node worker with the lock FD inherited. There is no separate helper left alive. The kernel holds the lock until the worker and its inherited FD users exit; its inode is never unlinked. The service checks pinned Python binary, inherited FD inode and actual shared/open-description lock ownership before irreversible admission stages. The marker/config are for a separately enrolled clean root only; no enrollment/installation or migration of existing roots is implemented. Windows retains existing manual-lock behaviour.
