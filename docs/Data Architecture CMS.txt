eninsula Insider — Sanity Data Architecture Report
Overview
Sanity is the CMS backend for the editorial core of the site. It sits alongside — not above — a second data layer: 20 Astro content collections stored as JSON/Markdown files in next/src/content/. The two systems share the same field vocabulary and the same {slug, data: {...}} envelope, but they serve different stages of the content lifecycle. Sanity wins when a document has been promoted there; the file system is the fallback and the staging area.

Field Group Patterns
Every document uses Sanity's groups API to organise the editing form. The consistent pattern across all types:

Editorial / Content (default tab — shown first): name, slug, editorial copy, hero image, tags
Location (venues, experiences): place reference, zone, coordinates, address, phone, website
Commerce / Booking (venues, events): price band, booking URL, provider, affiliate flags
Audience (events, experiences): suitable for, audience tags, kids grade, dog friendly
Authority (venues only): hats, Halliday score, awards, press
Admin (all): publishedAt, lastVerified, sitemapExclude
sitemapExclude: boolean appears on every document type — the sitemap generator filters by it.

Event Document — Special Architecture
Events have a deliberate three-tier field ownership model, annotated in the Astro schema:

Tier	Fields	Owner
Identity + facts	title, slug, summary, startDate, category, venueName, etc.	Import script (can overwrite)
Derived	nextOccurrence	Cron job (recomputed for recurring events)
Editorial overlay	editorNote, editorVerdict, kidsGrade, lens[], worthTheDrive, firstTimer, heroImage	Human editors (never overwritten by import)
The lens[] field (10 values: weekend-pick, date-idea, family-saturday, rainy-day, etc.) drives filtering on the what's-on page and the homepage weekend picks rail.

Venue — Type Vocabulary
15 types: restaurant, winery, cafe, bakery, pub, brewery, distillery, producer, market, hotel, villa, cottage, glamping, farm-stay, spa.

Wineries get three extra field groups not shown on other types: wines (variety/style data), visiting (cellar door hours/tasting fee), and restaurant/accommodation objects for on-site offerings.

Article — Body Content
Article bodies are Portable Text arrays. Beyond standard blocks (h2, h3, blockquote, bullet, numbered), the schema registers six custom embed types:

alertBlock — danger/warning/info callouts
practicalCallout — eyebrow + heading + body panels
cellarDoorList — cellar door list (JSON body, migrated from MDX)
dogPolicyTable — dog policy comparison (JSON body)
subregionGrid — subregion tiles (JSON body)
varietyGuide — grape variety guide (JSON body)
Dual-Source Architecture
The most important architectural point: Sanity and the file system coexist. The adapters in next/src/lib/sanity/ fetch from Sanity at build/request time using GROQ queries. If a document exists in Sanity, it wins over the JSON file. If not, the JSON file serves as the fallback.

Astro content collections with no Sanity counterpart (file system only):

localSecrets	Markdown	Reader-submitted, exported from Supabase
insidersThirty	JSON	Annual ranked list

signature-events	JSON	Evergreen anchor event pages
species, fishingLocations, fishingCharters, boatRamps, boatHire	Markdown	Fishing/boating vertical, all in draft status
The fetch pattern in adapters:

fetchAllVenuesFromSanity() → lightweight list (slug + publishedAt + sitemapExclude) for build-time static path generation
fetchVenueFromSanity(slug) → full document for detail page rendering
fetchAllExperiencesFromSanity() → lightweight only — no editorNote, no seasonBest (this is the root cause of the orphan image issue described earlier)
Known Technical Debt / Open Migration Items
itineraryStop.experienceSlug is a string, not a reference. Comments in the schema say "Phase 5 will convert these to proper Sanity references." The conversion hasn't landed.
Events, experiences, venues, and places all have Sanity schemas but the primary data for most still lives in JSON. The auto-create pattern (createPlaceFromLocalJson in sanity-patch.ts) progressively creates Sanity documents when editors first touch an image — only places have this wired up today.
Events have no Sanity image write path. The sanity-patch.ts handler has no createEventFromLocalJson fallback, so event hero images are orphaned in the admin overlay (the issue raised before this report).
Embed blocks stored as raw JSON strings (cellarDoorList, dogPolicyTable, etc.) are a migration shortcut. The comments note "editors can refine the props after cutover" — structured fields haven't been built for those types yet.
fetchAllExperiencesFromSanity() returns a sitemap-only stub. Any page that calls this function and then accesses full experience fields (like editorNote) will crash during prerender — as seen this morning.
Data Flow Summary
Build time:
  Sanity GROQ API → fetch*FromSanity() adapters → Astro pages (static HTML)
  src/content/*.json → getCollection() → Astro pages (static HTML)
Admin edit (runtime):
  Editor right-clicks image → admin overlay → /api/admin/image-binding (Supabase lookup)
    → /api/admin/sanity-patch → Sanity write client → patch doc → triggerRevalidate()
    → Vercel deploy hook → new build
Event data:
  Import script (JSON spreadsheet) → src/content/events/*.json → committed to Git
  Cron (nextOccurrence, lens recompute) → updates JSON in place → commits
