# Image Registry Migration

Generated: 2026-06-02

## Problem

Image selection had several competing sources:

- content `heroImage`
- CMS image slots (`hero` and `heroImage`)
- card-local fallback logic
- page `ogImage`
- Pagefind `meta.image`
- `pi.entity_index.hero_image`

That meant search tiles, cards, detail pages, saved items, and social metadata
could show different images for the same venue, place, event, or article.

## Durable Model

`src/data/image-registry.json` is now the central derived manifest. It is
generated by `scripts/generate-image-registry.mjs` from the current populated
content and baked CMS image overrides.

Priority order:

1. baked published CMS override: preferred field, then `hero`, then `heroImage`
2. usable content `heroImage`
3. deterministic fallback based on place/type

The registry preserves original content values in `originalHero`, records the
canonical served image in `canonicalHero`, and classifies quality via
`kind`, `source`, `hasOwnPhoto`, duplicate metadata, and missing-file flags.

## Current Consumers

- `resolveHero(...)` reads the registry when no live CMS override exists.
- Venue, place, and event cards use `resolveHero(...)`.
- Entity detail pages pass registry-backed heroes to `ogImage` and `searchImage`.
- `BaseLayout` emits Pagefind `meta.image` from `searchImage`.
- `refresh-entity-index.mjs` writes registry-backed `hero_image` to
  `pi.entity_index`.
- `audit_images.cjs` audits the registry rather than a partial folder scan.

## Migration Plan

1. Run `npm run image-registry` after content or baked CMS image changes.
2. Run `npm run lint:images` to review duplicate groups and fallback entities.
3. Mark legitimate shared images editorially by replacing the current implicit
   duplicate with a named shared asset group in content or future registry
   allowlist work. Good examples: estate-level reuse where a hotel, restaurant,
   and cellar door are genuinely part of the same property.
4. Replace accidental duplicates first:
   - placeholder images
   - category fallbacks
   - generic place/explore images used on specific venues
   - derived fallbacks for high-traffic entities
5. Once replacements are complete, tighten the audit:
   - warn on allowed shared groups
   - fail on unapproved duplicate own-photo usage
   - fail on placeholders or missing local files
6. Apply `npm run entity-index:apply` after the registry is clean enough for
   production search RPC refresh.

This migration does not delete or overwrite existing populated hero images.
It makes the current state inspectable and gives every surface one canonical
source to read.
